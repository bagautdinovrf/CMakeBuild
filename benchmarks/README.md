# FLTK vs Nana: бенчмарки CMakeBuild

Результат проверенной серии на этой машине: [RESULTS.md](RESULTS.md).

Запуск из корня проекта:

```powershell
powershell -ExecutionPolicy Bypass -File .\benchmarks\run.ps1
# Уже собранные бенчи, больше повторов:
powershell -ExecutionPolicy Bypass -File .\benchmarks\run.ps1 -SkipBuild -Repetitions 15
```

Скрипт находит CMake так же, как `build.ps1`; нестандартный путь можно передать
через `-CMakePath`. Он последовательно собирает **только** цели `FltkBench` и
`NanaBench` через пресеты MSVC Release x64 со статическим runtime. Исходники
панелей и закреплённые зависимости те же, что у готовых приложений. Готовые
`CMakeBuild.exe` и их версии не меняются: это добавление инструментов проверки,
а не изменение программ.

По умолчанию выполняется один прогрев каждой реализации, затем семь пар
измерений. Порядок чередуется: FLTK/Nana, Nana/FLTK. Каждый прогон — новый
процесс с новым INI и видимой панелью с журналом 620×365 логических пикселей на
одном мониторе. Окна появляются на время проверки. Для сопоставимого результата
не перемещайте их, не переключайте тему ОС и не запускайте тяжёлые приложения
во время серии. Подменять пользовательский INI не требуется; скрипт проверяет
его SHA256 до и после работы, включая обработку ошибок.

Результаты находятся в отдельной папке `build/engine-tests/benchmarks` с датой и
временем запуска: `report.md`, `report.csv`, `report.json`, исходные JSON каждого
прогона и журналы. `report.json` сохраняет метаданные машины, компилятора, версии
и commit зависимостей, исходные измерения и агрегаты. Размеры и SHA256 готовых
программ записываются отдельно от бенчмарков.

| Измерение | Что входит |
| --- | --- |
| `startup_ms` | От входа в бенчмарк до завершения первой нативной отрисовки: инициализация toolkit, отдельный INI, создание и показ панели |
| `process_first_frame_ms` | От запуска процесса скриптом до сигнала о первой отрисовке; включает создание процесса и опрос файла с номинальным интервалом 2 мс, который планировщик Windows может увеличить |
| `idle_cpu_ms_per_second` | Процессорное время процесса за 1,5 с простоя после 250 мс стабилизации, нормированное на секунду; 10 мс/с ≈ 1% одного ядра |
| `idle_private_mib`, `idle_working_set_mib` | Private Bytes и Working Set процесса перед нагрузкой журнала |
| Handles / GDI / USER | Количество ресурсов процесса перед нагрузкой |
| `log_total_ms`, `log_cpu_ms` | Полное время и CPU обработки 8192 строк: 128 пакетов по 64 строки, UTF-8, кириллица и emoji, автопрокрутка и обрезка старого вывода |
| `log_chunk_p50_ms`, `log_chunk_p95_ms`, `log_chunk_max_ms` | Длительность синхронной обработки одного пакета вместе с отрисовкой; показывает паузы UI при большом выводе |
| `log_private_mib`, `log_working_set_mib` | Память после нагрузки, включая одинаковые входные буферы самого бенчмарка |
| `redraw_p50_ms`, `redraw_p95_ms` | 64 полные перерисовки реальных виджетов с заполненным журналом |
| `theme_p50_ms`, `theme_p95_ms` | 32 смены светлой/тёмной палитры с отрисовкой и обработкой событий |

Основная таблица содержит медианы по независимым процессам. Дополнительный p95
по процессам показывает разброс серии; при семи повторах это максимальный
результат. Значения p50/p95 пакетов и кадров сначала вычисляются внутри каждого
процесса; их исходные выборки тоже сохраняются. Во всех метриках меньше — лучше.
Отношение Nana/FLTK > 1 означает большее значение у Nana; при нулевой базе
отношение не вычисляется.

Общий C++ harness, собранный с самым новым поддерживаемым диалектом, задаёт одинаковую нагрузку и независимо вычисляет ожидаемый
остаток журнала. Результат публикуется только после проверки **текста настоящего
виджета**, включая кириллицу и emoji, обрезки, DPI и неизменности размеров окна.
Для Nana CRLF снимка редактора нормализуются в LF. Скрипт дополнительно проверяет
совпадение компилятора, Release, DPI, размеров и параметров нагрузки у всех
прогонов. Ни один тестовый проект не собирается и не запускается.

Каждый пакет передаётся непосредственно в штатный путь обновления журнала и
сразу рисуется; очереди событий движка обходятся. Во время реальной сборки вывод
объединяется перед обновлением UI, поэтому длительность этого стресса не равна
времени обработки того же вывода в обычной сборке.

Измерения показывают эффективность **этих реализаций CMakeBuild**, а не всей
библиотеки во всех приложениях. Старт измеряется у отдельных harness EXE, а не
у поставляемых GUI EXE; окно изначально показывает журнал и не загружает
пользовательский проект. Кэш ОС прогрет; холодный запуск после перезагрузки
не измеряется. Отрисовка заканчивается на уровне toolkit/GDI (`GdiFlush`), без
ожидания вывода кадра DWM на экран. Пауза обработки пакета не равна задержке
реального пользовательского ввода. CMake и компиляция проекта не сравниваются:
их время определяется движком, компилятором и самим проектом.

Штатный таймер Nana остаётся активным, включая опрос темы ОС и обновление панели.
Если тик совпадает со сменой палитры, в измерение входит эта работа и возможное
восстановление системной темы. Бенчмарк не отключает таймер ради ускорения.
Начальная палитра обеих реализаций — системная. Нулевое CPU за короткий интервал
означает значение ниже чувствительности измерения, а не гарантированный нулевой
расход. Working Set зависит от состояния кэша ОС; для памяти сравнивайте также
Private Bytes. Разница в несколько процентов требует длинной повторной серии.
